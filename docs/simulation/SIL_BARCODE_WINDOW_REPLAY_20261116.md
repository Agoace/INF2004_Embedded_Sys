## Comparison method

The native application files are not edited. The host builds two source copies:
old `barcode_window.c/.h` from cbcb557 and new versions from52244f2. All other
compiled source/header hashes must match. New defaults are80mm forward,
77mm left and111mm track. Pure C code runs in both variants.

The host records each actual native acquisition input: ADC/time, original held
motor publication and timestamp, counters/faults, calibration and actual jlive
control values/tags. Motor publications are held at10ms;1ms encoder inputs are
**not** substituted or restamped. Bounded host-only arrays hold5300inputs,
128window events and256detail events; overflow fails the run/replay. Export is
after stepping. Actual acquisition and event arrays must match C replay.

For component comparison, both variants receive the **same** recorded input
and control/ACK stream. This isolates the reader; it is not a replay of each
variant's feedback path and is not repeated physics. The straight reference
stream is regenerated by the old native code, with every recorded vehicle and
motor output checked. No control permission, letter, verified flag or action is
injected. SHADOW, valid0 and no OFFSET_VERIFIED remain in force.

For every window/producer event, retain its actual reason and decoded letter.
A pre-bound window event is distinguished from a producer failure. For
BW_MOTION, use its original motor bracket to compute diagnostic GP28 net X
progress from recorded body pose and the flat80/77mm mount. Zero encoder delta
and net pose reversal are separate facts; the truth sign tolerance is1e-7mm.
No pose value enters C control. This diagnostic is not a hardware cause claim.

F is a valid letter, but the unchanged default map assigns commands only to
A/B/C/D. The day's arbitrary letter-command mapping is not supplied. Report
F decoding separately from the default unmapped command and actual admission;
never infer navigation correctness from a letter.
